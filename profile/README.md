# GitHub 컨벤션

## Linear 이슈 연결

- 작업 시작 전에 대상 Linear 이슈를 확인한다.
- 완료 보고에 대상 이슈의 식별자와 링크를 적는다.
- 대상 이슈가 없거나 확인되지 않으면 `없음` 또는 `미확인`으로 밝힌다.

## 브랜치 네이밍

- `main`/`develop`을 기본 브랜치로 사용한다.
- Linear 이슈가 있는 작업 브랜치는 `<type>/<소문자 이슈 식별자>-<영문 구현 내용>` 형식을 따른다. 예: `feature/dae-173-domain-entity-setup`.
- Linear 이슈가 없는 작업 브랜치는 `<type>/<영문 구현 내용>` 형식을 따른다. 예: `fix/header-bug`, `hotfix/payment-error`.
- 구현 내용은 영문 소문자 kebab-case로 간결하게 작성한다.
- type 종류: `feature`, `fix`, `hotfix`, `release`, `chore`, `docs`, `refactor`.

## 커밋 메시지 컨벤션

모든 저장소와 자동화 도구는 다음 형식을 사용한다.

```
<type>(<scope>): <subject>

[body]
```

- 프로젝트 저장소는 브랜치 흐름과 scope 후보만 추가로 정의할 수 있다.
- type 목록과 subject 문체는 프로젝트별로 다시 정의하지 않는다.

### Type

- 다음 type만 사용한다.
    - `feature`: 사용자 또는 시스템에 제공하는 기능 추가
    - `fix`: 잘못된 동작 수정
    - `refactor`: 동작을 유지한 코드 구조 개선
    - `test`: 테스트 추가·수정
    - `docs`: 문서만 변경
    - `chore`: 기능과 무관한 설정·도구·유지보수
    - `style`: 동작 변경 없는 서식·포맷팅 수정
- `perf`, `build`, `ci`, `init` 등 목록에 없는 type을 만들지 않는다.
- 성능 개선은 동작 변경 여부에 따라 `feature` 또는 `refactor`를 사용한다.
- 빌드, 의존성, CI 설정은 `chore`를 사용한다.

### Scope

- scope는 선택 사항이며 프로젝트가 정의한 모듈·도메인 이름을 사용한다.
- 여러 모듈에 걸친 변경이나 적절한 이름이 없는 변경은 scope를 생략한다.
- scope는 영문 소문자와 하이픈으로 작성한다.

### Subject

- 실제 커밋에 포함된 작업 내용만 한글 명사형으로 간결하게 작성한다.
- `구현`, `추가`, `수정`, `정리`, `제거`, `구성`, `연결`처럼 끝낸다.
- `한다`, `했다`, `합니다` 같은 서술형 종결과 마침표를 사용하지 않는다.
- 파일명 나열, 작업 과정, 감정, 완료 여부를 적지 않는다.

### Body

- 변경 이유, 선택 근거, 호환성 영향을 설명해야 할 때만 작성한다.
- subject를 반복하거나 변경 파일을 나열하지 않는다.

### 커밋 단위

- 하나의 커밋은 하나의 목적만 가진다.
- type이 다르거나 독립적으로 되돌릴 수 있는 변경은 분리한다.
- 서로 다른 기능·모듈·문서 주제의 변경을 한 커밋에 섞지 않는다.
- 기능과 직접 연관된 테스트는 기능 커밋에 포함할 수 있다. 테스트만 변경하면 `test`를 사용한다.
- WIP, fixup, 임시 디버깅 커밋은 push 전에 정리한다.

### 작성 절차

1. `git status`와 staged diff로 포함 파일을 확인한다.
2. staged 변경의 단일 목적에 따라 type과 scope를 결정한다.
3. subject가 실제 변경 전체를 대표하는지 확인한다.
4. 목적이 다른 파일이 섞였으면 커밋을 분리한다.

## Push 규칙

- push는 사용자가 명시적으로 요청한 경우에만 수행한다.
- push 전에 대상 브랜치, 커밋 범위, 원격 상태를 확인한다.
- 일반 push에는 릴리스 노트, annotated tag, 버전 변경을 추가하지 않는다.
- `-force`는 사용을 금지한다.
- `-force-with-lease`는 원격 브랜치를 덮어쓰는 부작용을 인지한 후에만 사용한다.

## PR 컨벤션

- 제목은 커밋 메시지 규칙과 동일한 `type: subject` 형식을 사용한다.
- 설명에는 변경 사항 요약, 대상 Linear 이슈의 식별자·링크, 테스트 방법을 포함한다.
- 최소 1인 이상 승인 후 머지한다.
- 머지 전략은 저장소별로 통일한다. Squash merge를 기본으로 하고, 릴리스 브랜치는 Merge commit을 사용한다.

## 코드 리뷰 규칙

- `CODEOWNERS` 파일로 파일·디렉터리별 필수 리뷰어를 지정한다.
- CI 통과, 코드 오너 승인, 미해결 코멘트 없음 모두를 리뷰 승인 조건으로 적용한다.
- 리뷰 코멘트에는 구체적인 개선 방향을 적는다.

## 버전 및 릴리스

- 버전 변경, 태그, 릴리스 노트, GitHub Release는 사람이 값과 범위를 명시적으로 요청한 경우에만 다룬다.
- 모든 annotated tag 메시지는 현재 배포 버전의 `주요 작업`과 직전 배포 버전 대비 `변경 사항`을 구분해 기록한다.
- 작업 완료와 일반 push는 릴리스로 간주하지 않는다.
- dev 배포가 성공하면 `vMAJOR.MINOR.PATCH-dev.N` annotated tag를 만들고 같은 목표 버전의 이전 dev tag보다 `N`을 1 높인다.
- prod 배포가 성공하면 `vMAJOR.MINOR.PATCH` annotated tag를 만든다.
- prod는 같은 목표 버전의 dev 배포가 성공한 source tree만 배포한다.
- 배포 tag는 검증과 health check가 모두 성공한 commit에만 만들며 이미 tag가 붙은 commit의 workflow 재실행은 새 버전을 만들지 않는다.
- Git tag는 릴리스 버전을, 배포 산출물의 commit SHA는 정확한 빌드 원본을 식별한다.
- 각 배포 가능한 저장소는 버전을 독립적으로 관리한다.
- 메이저 버전은 호환성을 깨는 변경에만 증가하며, 운영 배포 여부를 증가 기준으로 삼지 않는다.
- 하위 호환 기능은 마이너 버전, 하위 호환 수정은 패치 버전에 반영한다.

## 저장소 파일 관습

- `README.md`: 프로젝트 개요, 설치 및 실행 방법을 포함한다.
- `.gitignore`: 언어·프레임워크에 맞는 표준 템플릿을 사용한다.
- `AGENTS.md`: 해당 저장소의 AI 정책을 서술한다.
- `CLAUDE.md`: 필요하면 `@AGENTS.md` 임포트만 둔다.
